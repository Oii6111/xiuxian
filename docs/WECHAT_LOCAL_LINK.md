# 微信文字 → 灵宠任务：本地联调版

日期：2026-10-31。当前项目：`F:\godot\xiuxian2`。

## 1. 已经可以做什么

大模型地址和密钥稍后提供，不影响文字确认、结构化事件与任务展示的本地联调。本轮复用已上传的老人端真实 Python 消息处理代码，增加显式的任务事件适配扩展，接到真实 Godot 客户端。

可验证的流程：

```text
浏览器模拟微信文字传入
  → 老人端原消息入口
  → 补齐当前既有安排
  → 适配扩展输出最小计划事件
  → 独立联调任务投影
  → Godot 自动显示待反馈任务
  → 老人说明完成并确认
  → 输出本人自述事件
  → 同一任务更新为完成
  → 灵宠自动提示、任务页刷新
```

这里的浏览器只替代微信消息传输。**没有连接真实微信/OpenClaw，没有调用大模型，也没有接入 C 的正式账号、任务账本或奖励账本。** 联调任务投影是单次会话的内存数据，用于接口验证，不作为正式任务服务部署。

## 2. 怎么体验

运行 `tools/启动微信灵宠联调.cmd`。它启动本机随机端口的联调服务、打开模拟老人文字页面，并启动一个使用独立用户目录的游戏预览。

- 仅使用虚构信息；预览中使用“演示家人/联调守护者”，不载入正式账号。
- 在网页勾选同意共享本次虚构记录，然后依次输入：

```text
我最近在吃联调用药
每天一次
吃七天，饭后
我今天已经服药了
确认
```

第一句话后不会创建游戏任务；“每天一次”仍缺信息，也不会创建。补齐已知安排后才出现一项“记录今日既有用药安排”。完成候选在老人自己确认后同步完成，无需年轻人再审批。

可以尝试“我还没吃过药”：不会完成任务。“药吃完了”会先澄清是今天这次完成还是整个安排结束。

游戏中可以点击“今日任务”“下一步做什么”或“查看微信记录”。共享任务页只读，不通过原来的本地确认按钮再次发奖。关闭游戏会停止本轮联调服务；日志和虚构的老人端数据留在 `output/wechat-link-runs/session-*`。

启动环境需要 Python + Flask/requests，以及 Godot 4.7.2。可设置 `XIUXIAN_ACCOUNT_PYTHON` 和 `GODOT_BIN` 指定本机程序路径。命令行方式：

```powershell
python tools/wechat_link_demo/run.py --open-browser
```

## 4. 适配扩展处理的关键问题

1. **已知安排才启用。** 本地扩展要求明确的本人当前用药陈述、来源消息 ID、共享同意及完整的天数/次数/原有时间信息。缺少信息继续追问，不自动填7天；分多条补充时保留已知部分。
2. **共享权限。** `family_share=false` 的事件不出站。游戏投影不包含药名、剂量、测量数值、症状原文、图片或聊天记录。
3. **本人反馈。** 否定/疑问不产生完成事件；候选仍由老人自己确认。多个候选任务时，联调投影返回 `needs_clarification`，不随意选择一项完成。
4. **失败重试。** 事件先进入老人端独立 DB 的 `game_link_outbox`，只有收到成功且 ID 匹配的回执才记为已送达。失败保留待发送，联调工作器重试。
5. **账号隔离。** 游戏只能使用专用只读令牌；老人侧服务凭证不传给 Godot。快照必须匹配当前账号，旧会话/旧版本回复被丢弃；退出后清理。

上游老人助手的临床内容和模型质量不在本轮重新设计。当前联调使用确定的虚构句式；真实老人语言、语音和图片仍需 D 同学独立验收。计划变更、补记、跨日及多用药精确时段，正式接入时应对齐公共后端契约。

## 5. 游戏预留的任务读取接缝

设置完整读取 URL：`XIUXIAN_COMPANION_TASK_URL`。配套令牌为 `XIUXIAN_COMPANION_TASK_READ_TOKEN`，当前适配器放入 `X-Companion-Read-Token` 请求头。此令牌只能是玩家/家庭范围的只读凭证，不是 D 内部服务令牌或模型密钥。

这与自由聊天的 `XIUXIAN_COMPANION_API_URL` 是两个独立接缝。任务状态更新无需等待自由聊天接口；大模型地址和密钥配置在后端服务。

读取响应示例：

```json
{
  "schema_version": 1,
  "mode": "live",
  "account_id": "当前游戏账号ID",
  "revision": 3,
  "business_date": "2026-10-31",
  "members": [{
    "game_member_id": "对应本地老人角色ID",
    "tasks": [{
      "task_id": "稳定实例ID",
      "business_date": "2026-10-31",
      "title": "记录今日既有用药安排",
      "status": "completed",
      "completion_method": "wechat_self_report"
    }]
  }]
}
```

`status` 当前支持 `pending / completed / cancelled`。只接收已存在且已同意共享的游戏角色；不会根据网络数据自动创建老人。快照是只读投影，不调用本地 `record_task()`、不修改钱包。

联调夹具返回 `mode="local_demo"`，Godot 只有带显式 `--wechat-link-demo` 标志才接受；普通正式游戏拒绝这个模式。C 的现有 `/api/v2/snapshot` 和 `quests.list` 并不是上述原样结构，需要增加读取适配和账号/角色映射，不能直接替换 URL 就宣称已接正式服务。

## 6. 和队友的真实服务怎样继续对接

1. D 审阅本地 `sidecar_adapter.py`，将“确认计划、完成反馈、结束计划”的最小事件出口接到真实老人服务；保留授权和来源 ID。实际微信 hook 还需传入稳定 `message_id`。
2. C 提供权威计划/任务存储及事件接收适配，把 D 的老人 ID、有效绑定、C角色和本地游戏角色对应起来；保持当前本地游戏的100灵气等规则。
3. C/网关返回第5节对应的读取投影，并提供经验证、按账号限权的访问凭证。正式环境使用 HTTPS，绑定撤回与状态恢复由服务端处理。
4. 微信真实通道在队友服务中启用，游戏读取同一服务端结果；一位测试老人先跑通，再扩展两位老人。
5. 模型配置就绪后，在 D 服务验证自然聊天和视觉识别；本地演示启动器始终禁用外部模型。

因此，本轮完成的是**可运行的本地文字预对接**，不是微信账号已登录、C正式账本已迁移或小游戏已经发布。
