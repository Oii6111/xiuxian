# 《疯狂修仙，中》架构与模块划分

> 版本 v0.2 · 2026-10-30（新增任务系统）
> 两条切分轴：**横向分层（能力）** + **纵向板块（价值交付）**。
> 分层是地基，板块是垂直切片；板块之间不互相调用内部实现，只通过契约通信。

---

## 1. 分层架构（地基）

```
L5  内容层 Content          纯数据表（功法/技能/任务/成就/剧情/数值曲线）
L4  表现层 Presentation     视图与输入：只读状态，只发 Intent
L3  编排层 Orchestration    玩法流程：境界推进 / 任务追踪 / 赛季 / 庆典 / 限额
L2  规则层 Rules            纯计算：无节点、无 IO、可单测、可回放
L1  领域层 Domain           状态与事实：角色 / 计划 / 事件 / 授权 / 账本 / 任务
L0  内核层 Kernel           时间 / 事件 / 随机 / 配置 / 存档 / 审计
```

**硬约束**

1. L2 及以下禁止 `get_node`、禁止访问 UI、禁止直接读文件。
2. L4 禁止直接改状态，只能发 Intent。
3. 依赖只能向下，同层之间通过接口通信。
4. 每个板块只能**调用**共享服务，不能复制实现。

---

## 2. 共享服务（不属于任何板块）

| 服务 | 层 | 独占职责 | 被谁使用 |
|---|---|---|---|
| `Clock` | L0 | 现实时间 / 游戏日 / 时间窗 / 宽限日 / 重置点 | 全部 |
| `EventBus` | L0 | 类型化信号 | 全部 |
| `Rng` | L0 | 种子化随机，可复现 | 战斗、掉落 |
| `Registry` | L0 | 只读配置表 | 养成、战斗、任务、剧情 |
| `Store` | L0 | 存档与版本迁移 | 全部 |
| `Ledger` | L1 | **唯一记账方**：去重键、奖励流水、上限计数 | 养成、战斗、任务、社交、剧情 |
| `Consent` | L1 | **唯一授权方**：可见性、撤回 | 社交、剧情、健康事件 |
| `AttributePipeline` | L2 | **唯一属性结算方**：基础→功法→法器→Buff | 养成、战斗 |
| `RewardEngine` | L2 | **唯一发奖方**：奖励请求→资格→奖励 | 养成、任务、剧情、社交 |
| `CombatResolver` | L2 | **唯一伤害结算方**：回合纯函数 | 战斗（渡劫 / Boss 共用） |
| `LifecycleFSM` | L2 | **唯一状态迁移方**：合法迁移表 | 剧情、养成、战斗、任务 |
| `ObjectiveEvaluator` | L2 | **唯一条件求值方**：布尔表达式 + 计数目标 | 任务、剧情、成就 |
| `AbuseControl` | L3 | 跨系统限额、去重策略 | 养成、战斗、任务、社交 |

> 六条铁律：只有 `Ledger` 记账、只有 `RewardEngine` 发奖、只有 `CombatResolver` 算伤害、只有 `Consent` 定可见性、只有 `LifecycleFSM` 改状态、只有 `ObjectiveEvaluator` 判达成。

---

## 3. 板块一：角色养成

**目标**：把长辈的健康行为转化为角色成长，形成可展示的长期积累。

### 3.1 子模块

| 子模块 | 层 | 职责 |
|---|---|---|
| 资源账本 | L1 `Ledger` + 资源模型 | 守护修为 / 灵气 / 守护符 / 家族灵印的余额与流水 |
| 属性结算 | L2 `AttributePipeline` | 根骨、灵力、心境、机缘、战斗力 |
| 境界推进 | L3 `Progression` | 炼气→筑基→金丹→元婴→化神→渡劫→飞升 |
| 装备槽位 | L1 槽位模型 + L5 表 | 功法槽、法器槽、解锁条件 |
| 稳定 Buff | L1 Modifier + L3 连续天数 | 7/30/100 天加成，休养时暂停不清零 |
| 养成面板 | L4 视图 | 角色卡、属性明细、来源标注 |

### 3.2 对外接口

```gdscript
func get_stats() -> ResolvedStats        # 给战斗系统
func get_loadout() -> Loadout            # 功法/法器/技能
func apply_reward(delta: RewardDelta)    # 由 RewardEngine 产出后调用
signal realm_changed(old_realm, new_realm)
signal resource_changed(kind, value)
```

### 3.3 边界

- ❌ 不做奖励资格判定（属于 `RewardEngine`）
- ❌ 不做战斗结算（属于 `CombatResolver`）
- ❌ 不做洞府的社交交互（属于社交板块，养成只提供展示快照）

### 3.4 MVP

资源收支 + 七阶境界 + 五维属性 + 7/30/100 天 Buff，界面给一张角色卡。

---

## 4. 板块二：战斗系统

**目标**：用 3–5 分钟短局承载「渡劫」与「世界 Boss」两种战斗场景。

### 4.1 子模块

| 子模块 | 层 | 职责 |
|---|---|---|
| 战斗核心 | L2 `CombatResolver` | 回合制纯函数：伤害、护盾、灵气、阶段 |
| 战斗配置 | L5 `skills.tres` | 雷诀 5 灵气/80 伤害、镇心诀 3/120 盾、回春符 4/转中性 |
| 渡劫编排 | L3 + `LifecycleFSM` | 日常→待确认→复测→开劫→准备→进行→庆典/休养/羽化 |
| Boss 活动 | L3 `Activity` | 赛季开期、四阶段、共享血条、每日 3 次、贡献结算 |
| 战斗表现 | L4 `CombatView` | 动画、飘字、镜头、结算面板 |
| 贡献记账 | L2 → L1 `Ledger` | 个人贡献与全服进度 |

### 4.2 对外接口

```gdscript
func resolve(state: CombatState, action: Action) -> CombatResult   # 纯函数
func start_tribulation(chapter_id: String) -> void
func boss_battle(loadout: Loadout) -> BossContribution
signal combat_finished(result)
```

### 4.3 边界

- ❌ 不产出养成资源（战果只产出贡献与解锁，资源由 `RewardEngine` 给）
- ❌ 不判断「是否进入渡劫」（由健康事件 + 家属确认决定）
- ❌ 不排名医疗数据（榜单只统计游戏贡献）

### 4.4 MVP

三回合渡劫 + 单阶段 Boss；两场战斗共用同一个 `CombatResolver`。

---

## 5. 板块三：社交系统

**目标**：让家庭故事被看见、被纪念，同时不泄露医疗隐私。

### 5.1 子模块

| 子模块 | 层 | 职责 |
|---|---|---|
| 可见性与授权 | L1 `Consent` | 谁能看什么、可撤回 |
| 洞府展示 | L4 + L1 展示快照 | 门匾、成就、修行碑、限定装饰 |
| 互动 | L1 动作表 + L3 `AbuseControl` | 点赞、留言、赠送装饰（不影响战力） |
| 榜单 | L3 `Ranking` | 贡献榜、策略榜、协作榜、连续参与榜、洞府创作榜、收集榜 |
| 庆典与纪念 | L3 `Ceremony` | 渡劫庆典、羽化纪念（双确认 + 冷静期 + 默认私密） |

### 5.2 对外接口

```gdscript
func publish(snapshot: ShowcaseSnapshot, scope: ConsentScope) -> void
func visit(cave_id: String) -> CaveView
func react(target_id: String, kind: String) -> void
signal ceremony_opened(kind)   # demo: tribulation | memorial
```

### 5.3 边界

- ❌ 不产生战斗资源，不进竞技排行（羽化纪念明确不产出）
- ❌ 不公开原始健康数据，不做「谁家老人更健康」榜
- ❌ 羽化不由系统自动判定，必须家属二次确认
- ❌ 不定义成就，只展示成就（定义与判定归任务系统）

### 5.4 MVP

洞府页 + 点赞留言 + 三个榜单；庆典用弹窗演示。

---

## 6. 板块四：主线剧情

**目标**：把「异常→复测→渡劫→恢复→庆典」这条家庭叙事串成可推进的篇章。

### 6.1 子模块

| 子模块 | 层 | 职责 |
|---|---|---|
| 章节模型 | L1 `ChapterState` + L2 `LifecycleFSM` | 篇章阶段与合法迁移 |
| 剧情节点 | L2 `ObjectiveEvaluator` + L5 剧本表 | 触发条件、前置、奖励引用 |
| 对话与 NPC | L4 + L5 文本表 | 街区 NPC 对白、天机碑提示 |
| 引导解锁 | L3 `Progression` 钩子 | 章节完成解锁功能、场景与任务组 |
| 叙事编排 | L3 | 把健康事件、渡劫、庆典串成一条时间线 |

### 6.2 对外接口

```gdscript
func chapter_state() -> ChapterState
func advance(node_id: String) -> Result
func on_event(topic: Topic, payload: Dictionary) -> void
signal chapter_advanced(chapter_id)
```

### 6.3 边界

- ❌ 不写死数值，奖励一律走 `RewardEngine`
- ❌ 不直接改角色状态，只发事件
- ❌ 不替代医学判断：异常只触发提示与复测
- ❌ 不做可重复目标（那是任务系统），主线只做一次性推进

### 6.4 MVP

三章：初入修途 → 风起（异常与复测）→ 破劫归元（渡劫与庆典）。

---

## 7. 板块五：任务系统

**目标**：用可重复的目标驱动日常循环，把现实行为、游戏行为和成就统一成一种声明式结构。

### 7.1 子模块

| 子模块 | 层 | 职责 |
|---|---|---|
| 任务定义 | L5 `quests.tres` | 日常 / 周常 / 一次性 / 成就；目标、前置、奖励引用 |
| 任务状态 | L1 `QuestState` | 未接取 / 进行中 / 可领取 / 已完成 / 已过期 |
| 条件求值 | L2 `ObjectiveEvaluator` | 布尔表达式 + 计数目标，纯函数，与主线共用 |
| 进度追踪 | L3 `Tracker` | 订阅 `EventBus`，更新计数，处理每日/每周重置 |
| 领奖 | L2 `RewardEngine` | 任务只产出 `RewardRequest`，不直接发奖 |
| 任务面板 | L4 | 列表、进度条、一键领取、跳转目标 |

### 7.2 对外接口

```gdscript
func list_available(filter: QuestFilter) -> Array[QuestView]
func progress(quest_id: String) -> QuestProgress
func claim(quest_id: String) -> Result        # 内部转成 RewardRequest
func on_event(topic: Topic, payload: Dictionary) -> void
signal quest_completed(quest_id)
```

### 7.3 边界

- ❌ 不定义健康计划（`Plan` 是现实事实，任务只能引用，不能创建）
- ❌ 不做叙事推进（那是主线剧情）
- ❌ 不发奖励（只产出请求，由 `RewardEngine` 结算）
- ❌ 不做展示（成就的展示归社交系统的洞府）

### 7.4 三者的区别（最容易混）

| | 健康计划 `Plan` | 任务 `Quest` | 主线 `Chapter` |
|---|---|---|---|
| 来源 | 现实医嘱 / 家属设置 | 策划配置表 | 策划剧本表 |
| 性质 | 事实，不可伪造 | 可重复、可重置 | 一次性、线性 |
| 完成判定 | 外部事件 + 人工确认 | `ObjectiveEvaluator` | `ObjectiveEvaluator` + FSM |
| 产出 | 触发健康事件 | 奖励请求 | 解锁 + 叙事推进 |
| 归属 | 健康事件（L1） | 任务系统 | 主线剧情 |

> 成就 = 一次性任务（判定归任务系统）+ 展示（归社交系统）。

### 7.5 MVP

5 条日常 + 3 条周常 + 5 个成就；本地按 `Clock` 重置；领取走 `RewardEngine`；面板能跳转到目标场景。

## 8. 板块间契约

| 方向 | 契约 |
|---|---|
| 健康事件 → 养成 | `RewardEngine` 产出 `RewardDelta`，养成调用 `apply_reward()` |
| 健康事件 → 任务 | 事件进入 `EventBus`，`Tracker` 更新相关任务进度 |
| 养成 → 战斗 | 只传 `ResolvedStats` + `Loadout`，不传节点 |
| 战斗 → 养成 | 回传 `BossContribution` 与解锁标记，不回传资源 |
| 战斗 → 任务 | 战斗结束事件可满足「参战一次」类目标 |
| 主线 → 任务 | 章节完成解锁任务组（`unlock_quest_group`） |
| 任务 → 养成 | 只发 `RewardRequest`，不直接改资源 |
| 主线 → 全部 | 只发领域事件（`chapter_advanced`、`tribulation_started`） |
| 社交 → 全部 | 只读展示快照，写操作经 `Consent` 与 `AbuseControl` |
| 全部 → 存档 | 统一经 `Store`，禁止各自序列化 |

---

## 9. 实现顺序

```
1. L0 + L1 共享服务（Clock/EventBus/Ledger/Consent/Store）
2. 角色养成（属性管线 + 境界 + 资源）
3. 主线剧情骨架（章节 FSM + 事件订阅）
4. 任务系统（ObjectiveEvaluator + Tracker + 面板）
5. 战斗系统（CombatResolver + 渡劫 + Boss）
6. 社交系统（洞府 + 互动 + 榜单 + 庆典）
7. 表现层统一瘦身（Intent / ViewModel）
```

任务系统依赖 `EventBus` 与 `RewardEngine`，建议排在主线骨架之后、战斗之前——因为渡劫与 Boss 的任务目标需要先有追踪器。
