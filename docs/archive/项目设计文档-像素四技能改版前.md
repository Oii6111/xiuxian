# 《家族修真录》项目设计文档

> 长辈在现实中修行，子女在游戏中渡劫。

## 0. 文档状态

- 文档用途：黑客松项目讨论、产品设计、Demo 实现和路演答辩底稿。
- 目标形态：打开网页即可运行的单页 Web Demo。
- 当前 Demo 数据：使用模拟健康事件和模拟硬件事件，不连接真实医疗设备。
- 医疗边界：产品不替代医生，不用于诊断、处方、急诊判断、服药依从性判定或死亡判定。

## 1. 项目概述

《家族修真录》是一款面向年轻人的家庭健康游戏化产品。年轻人为父母或祖父母创建修仙角色，长辈现实中完成适合自己的健康管理行为，系统将这些行为转化为修为、灵气、守护符和家族成就，推动年轻人的角色养成、短局渡劫和全服世界 Boss 活动。

玩家不是在游戏里控制老人，也不是通过游戏替老人做医疗决定。玩家做的是：了解家人的状态、使用家人产生的支援、在游戏中做策略选择，并把长期健康管理变成可见、可分享、可纪念的家庭故事。

核心闭环：

```text
长辈完成个人健康计划
        ↓
拍照 / 模拟硬件事件 / 家庭确认
        ↓
AI 识别、整理、核验、解释
        ↓
生成修为、灵气、守护符和成就
        ↓
年轻人养成角色、参加渡劫和世界 Boss
        ↓
洞府展示、社群比较、家庭庆典或羽化纪念
        ↓
年轻人获得持续关心家人的游戏动机
```

## 2. 用户与角色

### 2.1 年轻人

- 唯一的游戏操作人。
- 为家中长辈创建角色。
- 进入三维街区、移动、探索、战斗、参加世界 Boss。
- 选择何时使用长辈带来的守护资源。
- 决定哪些成就、状态和纪念内容公开给社群。

### 2.2 长辈

- 健康管理的现实受益者。
- 不要求长期使用游戏。
- 可以通过硬件、照片、家庭成员确认等方式产生健康事件。
- 需要对健康数据的分享范围和纪念内容拥有授权、撤回或修改权。

### 2.3 一个年轻人可以管理多个角色

Demo 先支持一个年轻人管理一位长辈。产品后续可以允许一个玩家创建父亲、母亲、祖父母等多个角色，每个角色有自己的计划、修行记录、洞府和隐私设置。

## 3. 世界观与叙事

现实世界中，每个人都在修行：

- 长期疾病患者的规律监测、按计划用药、复诊和生活调整，是长期修行。
- 健康人的规律作息、运动、饮食和体检，是巩固根基。
- 短期疾病或阶段性恢复，是一段有起点和终点的渡劫。
- 恢复得到可靠来源确认后，举办渡劫庆典。
- 长辈去世后，家属可以主动封存角色，举办羽化大典或赛博纪念仪式。

叙事原则：

> 游戏中的境界代表长期积累，不能被一次异常数据抹掉；游戏中的战斗胜负代表一局策略挑战，不能替代医学结论。

## 4. 核心功能

### 4.1 家族角色创建

年轻人选择角色昵称、亲属关系、初始门派和外观，设置健康数据可见范围。Demo 可直接预置一位长辈样例，也可以让用户通过表单创建角色。

角色卡显示：

- 角色名和亲属关系；
- 当前境界；
- 战斗力；
- 修行天数；
- 最近一次计划完成状态；
- 洞府入口；
- 当前是否处于渡劫、休养或纪念状态。

### 4.2 拍照作为唯一健康入口

支持拍摄或上传：

- 体检报告；
- 药盒或处方；
- 医嘱或康复计划；
- 健康设备界面；
- 复诊单或阶段记录。

AI 先生成“待确认草稿”，抽取项目名、数值、单位、日期、药品名、频次和计划信息。低置信度字段必须标记为待确认，不能直接发放奖励。

Demo 可以使用预置图片和预设 OCR 结果，重点展示从照片到结构化事件的过程，不把 Demo 结果包装成临床识别准确率。

### 4.3 预留硬件事件接口

硬件接入只需要在 Demo 中提供标准事件接口。未来血压计、血糖仪、手环或其他设备可以通过适配层发送统一事件。

```json
{
  "event_id": "evt_001",
  "person_id": "elder_001",
  "event_type": "planned_measurement_completed",
  "observed_at": "2026-10-29T08:30:00+08:00",
  "source": "mock_device",
  "plan_id": "plan_daily_001",
  "status": "completed",
  "value": null,
  "unit": null,
  "confidence": 0.98,
  "consent_scope": "family_game",
  "review_status": "confirmed",
  "safety_flag": false
}
```

奖励主要判断“是否完成适合个人的计划”，不根据单次读数的绝对高低发放奖励。设备数据也不证明动作质量、测量姿势或已经服药。

### 4.4 AI 多 Agent

1. **视觉解析 Agent**：提取照片中的文本、日期、单位和候选项目。
2. **档案 Agent**：整理健康时间线、去重、关联个人计划。
3. **安全核验 Agent**：检查单位矛盾、低置信度字段和危险提示。
4. **生活建议 Agent**：用通俗语言解释记录，并给出下一步沟通或复测建议。
5. **游戏编排 Agent**：把已确认事件转成修为、支援卡、渡劫剧情和世界 Boss 反馈。

固定规则和人工确认负责奖励上限、红旗症状、改药禁止、治愈确认和羽化确认。模型不能自行宣布诊断、治愈或死亡。

## 5. 平时修行系统

### 5.1 资源

| 资源 | 作用 |
|---|---|
| 守护修为 | 提升境界和基础属性 |
| 灵气 | 用于短局战斗、渡劫技能和世界 Boss |
| 守护符 | 一次性护盾、恢复、破阵或改写事件的支援卡 |
| 家族灵印 | 解锁门匾、洞府外观、称号和家族故事 |

示例规则：每个经过核验的主行为获得 10 点守护修为、4 点灵气和 1 枚家族灵印。每天最多计 1 个主行为和 1 个辅助行为，同类事件 24 小时内去重，每周设置上限。

### 5.2 境界

```text
炼气 → 筑基 → 金丹 → 元婴 → 化神 → 渡劫 → 飞升
```

境界提升可以解锁：

- 新功法和技能槽；
- 新法器；
- 新洞府区域；
- 新角色动作；
- 世界 Boss 入场资格；
- 新剧情和收藏内容。

### 5.3 角色属性

- **根骨**：生命和耐久；
- **灵力**：技能资源上限；
- **心境**：抵抗负面事件；
- **机缘**：探索和掉落概率；
- **战斗力**：面向社群展示的综合数值。

属性由修为、功法、法器和稳定管理 Buff 共同决定，不将某个医学指标直接等同于某个属性。

### 5.4 稳定管理 Buff

保留“状态稳定会持续加数值”的产品愿望，但改成有限的游戏 Buff：

- 连续 7 天完成个人计划：+5% 护盾；
- 连续 30 天：+10% 护盾；
- 连续 100 天：+15% 上限；
- 进入休养或渡劫时 Buff 暂停，不清除历史修为。

这样可以奖励长期坚持，也不会让基础疾病更重的人天然输给健康人。

### 5.5 成就与洞府展示

| 现实积累 | 游戏展示 |
|---|---|
| 连续 7 天 | “初入修途”称号、第一块门匾 |
| 连续 30 天 | “一月守心”法相 |
| 连续 100 天 | 洞府特效、修行碑记 |
| 完成一次计划内复诊 | “问道寻医”成就 |
| 完成一段恢复计划 | “破劫归元”称号 |
| 家庭共同管理半年 | “家族同修”限定装饰 |

其他玩家可以参观洞府、点赞、留言、赠送不影响战斗的装饰和参加家庭庆典。排行榜展示游戏贡献、洞府创作和收藏进度，不公开原始医疗数据。

## 6. 网页街区与可操作小人

### 6.1 参考网页观察结果

参考页：[万圣酒会街区](http://47.111.163.198/town/)。本次观察到的前端架构特征：

- `/town/` 是单页应用入口，页面挂载在 `#app`；
- 角色选择/通行证表单使用独立的 `reception.html?embedded=1` iframe；
- 进入街区后使用一个全屏 Canvas 渲染三维场景；
- 当前 Canvas 暴露的无障碍标签是“新港旧街三维场景，WASD 移动，拖动观察”；
- HUD、按钮、对话框、名片和消息面板使用 DOM 覆盖在 Canvas 上；
- 页面通过 module script 和多个拆分模块加载；
- 资源中可以看到 `three-core`、`three-renderer`、`three-addons`、`world`、`geometry`、`citizen-behavior`、`presence-sync`、`resident-ghosts`、`identity`、`appearance`、`effects`、`dispose` 等模块；
- 交互包括 WASD 移动、Shift 加速、E 动作、拖动旋转视角、点击 NPC 查看资料、碰杯、聊天和查看名片；
- 动作面板提供 1—6 快捷动作，例如鞠躬、坐下、开合跳和环顾四周。

这些观察表明，它不是一张普通的二维表单页面，而是“3D Canvas 场景 + DOM HUD + 事件状态层 + 实时角色/在线同步”的结构。

### 6.2 《家族修真录》的网页实现建议

建议采用：

- **Vite + React + TypeScript**：前端构建和组件化；
- **Three.js**：三维地图、角色、摄像机、灯光和动画；
- **React DOM HUD**：顶部导航、角色卡、健康事件面板、洞府、排行榜和战斗弹窗；
- **Zustand 或轻量状态机**：集中管理玩家、角色、事件、战斗和社群状态；
- **REST API**：接收健康事件、查询档案和保存游戏状态；
- **WebSocket 或 SSE**：后续用于在线玩家、世界 Boss 共享血条和活动广播；
- **IndexedDB/localStorage**：Demo 先保存角色、事件和游戏进度；
- **Canvas 资源**：先使用低多边形或像素风角色和简化街区，避免制作完整 MMORPG。

## 7. 三维街区玩法设计

街区是年轻人日常打开游戏后的主要入口。玩家可以：

- 用 WASD 移动角色；
- 用 Shift 短暂加速；
- 拖动鼠标旋转摄像机；
- 走到洞府、渡劫台、世界 Boss 传送阵和排行榜石碑附近；
- 点击或按 E 与 NPC、建筑、道具交互；
- 使用 1—6 快捷动作进行展示；
- 点击其他玩家查看角色公开卡片；
- 发起碰杯、留言或参观洞府。

Demo 首版只需要一张小型街区：

1. **出生点**：展示项目口号和当前角色。
2. **家族洞府**：查看长辈的修行天数、成就和门匾。
3. **渡劫台**：进入当前恢复篇章。
4. **世界 Boss 传送阵**：参加全服活动。
5. **天机碑**：展示战斗力、策略榜和家族协作榜。
6. **纪念亭**：展示庆典和羽化纪念入口。

## 8. 渡劫系统

### 8.1 状态机

```text
日常修行
  ↓
需关注 / 待确认
  ↓
复测或联系医生
  ↓
家属确认开启渡劫
  ↓
渡劫准备
  ↓
渡劫进行
  ├── 恢复确认 → 渡劫庆典
  ├── 恢复较慢 → 闭关 / 休养
  └── 家属确认去世 → 羽化纪念
```

一次异常数据不能自动变成“生病”；没有上传数据也不能自动变成“死亡”。

### 8.2 三到五回合短局

玩家每天配置功法、法宝和护符，在 3—5 分钟内完成一局战斗：

- 雷诀：消耗 5 灵气，造成 80 伤害；
- 镇心诀：消耗 3 灵气，获得 120 护盾；
- 回春符：消耗 4 灵气，将一次负面事件转为中性；
- 守护符：由长辈完成计划行为后产生，可在关键回合使用。

玩家需要选择：立即输出、保留支援应对狂暴阶段，或用资源保护当前状态。

### 8.3 康复庆典

恢复得到可靠来源确认后，解锁：

- “破劫归元”称号；
- 烟花和庆祝动画；
- 家族合影位；
- 洞府限定装饰；
- 亲友留言册；
- 恢复纪念卡。

## 9. 世界 Boss

### 9.1 活动结构

每周或每 10 天开启一次活动，持续 3—7 天。全服共享一个 Boss 的总血量，Boss 有四个阶段：普通攻击、护盾、持续伤害和狂暴。

每个玩家每天 3 次出战机会。每次战斗选择 3 个功法或法器，并使用自己的守护资源。

示例结算：

```text
技能基础伤害 80
角色战斗系数 1.2
守护符加成 20
本次贡献 = 80 × 1.2 + 20 = 116
```

健康事件转化的支援最多贡献个人总伤害的约 25%，其余来自角色成长和战斗决策。

### 9.2 榜单

- 世界 Boss 贡献榜；
- 战斗策略榜；
- 家族协作榜；
- 连续参与榜；
- 洞府创作榜；
- 法器收集榜。

不设置“谁家的老人更健康”榜单，不按绝对血压、血糖、疾病严重度、康复速度或上传次数排名。

## 10. 奖励、公平与防刷

- 使用 `event_id`、图片哈希和时间窗去重；
- 同一计划事件每日只计一次；
- 奖励按个人计划和时间窗结算；
- 异常重复测量不能无限增加资源；
- 每日、每周设置奖励上限；
- 连续天数允许宽限日，不鼓励过量监测；
- 新玩家有基础灵气和追赶加成；
- 没有新健康数据时仍可玩普通战斗；
- 长辈暂时休息不会扣年轻人生命值；
- 世界 Boss 失败不影响现实健康评价。

## 11. 社群、庆典和羽化纪念

玩家可以参观洞府、查看公开成就、留言、送装饰、参加世界 Boss 和庆典。

羽化纪念必须满足：

- 家属主动确认；
- 至少二次确认和冷静期；
- 默认私密；
- 可撤回或关闭公开访问；
- 角色、生平修行碑、成就和家族故事保留；
- 不产生战斗资源，不进入竞技排行；
- 不由异常数据、长期失联或没有上传自动触发。

## 12. Demo 最小闭环

建议只做一条能在 3—5 分钟讲清的故事：

1. 年轻人创建“青松真人”；
2. 拍摄预置体检报告；
3. AI 展示抽取结果并让年轻人确认；
4. 模拟硬件发送“按计划完成一次测量”；
5. 角色获得修为、灵气和家族灵印；
6. 洞府解锁一个可参观的“百日守心”成就；
7. 模拟短期异常，系统只提示复测或联系医生；
8. 家属确认进入渡劫；
9. 年轻人用守护符完成三回合渡劫；
10. 模拟恢复确认，举办庆典；
11. 进入三维街区，通过传送阵参加世界 Boss；
12. 展示角色战力、个人贡献和家族协作榜。

| 成员 | 负责内容 |
|---|---|
| 医学与产品负责人 | 健康事件定义、医学边界、用户旅程、答辩材料 |
| 游戏机制负责人 | 修行、渡劫、世界 Boss、数值和平衡 |

## 14. 答辩重点

项目最重要的三句话：

1. **传统健康 App 让年轻人被动查看父母的数据；我们让父母每一次认真管理自己的健康，都成为子女游戏里的力量。**
2. **健康行为决定资源，年轻人决定策略；异常数据只触发确认和建议，不直接决定游戏价值。**
3. **修行让长期坚持有东西可展示，渡劫让恢复过程有故事，庆典和羽化纪念让家庭经历有地方安放。**

必须主动说明的设计冲突：

- 健康越好不等于战力越高，长期坚持个人计划才是主要成长来源；
- 社交比较只比较游戏贡献、策略和创作，不公开医疗隐私；
- 长辈不需要成为游戏玩家，但必须保留授权、撤回和分享控制；
- 游戏胜利不等于医学治愈，羽化纪念也不能由系统自动判定；
- 世界 Boss 的健康资源占比有限，避免催促老人过量监测。

## 15. 参考网页架构结论

参考网页提供的最适合借鉴的不是具体视觉主题，而是交互结构：

```text
角色选择/身份准备
        ↓
独立的入场表单或 iframe
        ↓
Three.js Canvas 三维街区
        ↓
键盘移动 + 鼠标视角 + E 交互
        ↓
DOM HUD 覆盖层
        ↓
NPC / 在线玩家 / 名片 / 聊天 / 动作菜单
        ↓
实时状态与社交同步
```

《家族修真录》可以沿用这个模式，把“街区”替换成修仙城，把 NPC 和建筑替换为洞府、渡劫台、世界 Boss 传送阵、天机碑和纪念亭。第一版不需要完整在线 MMORPG，只要有一张可走动的小地图、一个可控制角色、三处可交互建筑、一个战斗面板和一个共享榜单，就能证明核心概念。
